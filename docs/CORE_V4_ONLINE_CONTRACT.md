# V4 模型合同与 Link 对接职责

本文于 2026-11-02 按双方讨论修订。Core 定义模型输入和推理合同，Link 负责实际服务器消息、可见状态与智能体流程。此前说明将真实服务器的验收要求过多归入了 Core 待办，本版按实际职责重新整理

## 两类来源分别处理

| 来源 | 接入方式与责任 |
| --- | --- |
| 真实 YGOPro 兼容服务器 | Link 处理连接、封包、布局、刷新缓存、公开提示与玩家观察，分别适配实际服务器 |
| Core 托管的受控对局 | 需要接入时优先复用 Core 已有的受控对局与响应接口，类似 WindBot 的调用方式，由该来源明确提供哪些数据 |
| 本地 V4 制品 | Link 独立加载 PTH／ONNX 和运行资产，不在运行时导入 Core 仓库 |

受控 Core 对局的目标是使用既有操作接口，不要求它模拟真实公共服务器的所有行为。独立的 Link 专用 Core 服务转换层目前不作为架构重点，也不作为本轮任务

## Core 的合同范围

Core 维护以下模型合同，Link 按已有定义适配

- 输入字段、dtype、形状、候选顺序、掩码与响应编码
- 决策玩家、回合玩家、先手身份和双方回合计数的含义
- 动态卡片属性、稳定构筑、剩余构筑、事件历史和公开上下文的既有语义
- 未知、隐藏、已知零及失效状态在模型输入中的表达方式
- 模型协议、结构修订、哈希和语义坐标系兼容规则

本轮核对到 Core 提交 `f83f700e1624dda70531d6bdb51b5fd40e3d4916` 及版本标记为 3.16.3 的当前工作区。网络结构与 V4 输入结构仍沿用协议 4、结构修订 14，不能按框架软件版本选择模型结构

Core 已增加语义兼容清单。Link 会核验卡密前缀、标签编号和向量编码器合同后允许 PTH 内容更新；ONNX 保持图内导出语义，Link 3.3.3 起对外部词表追加和语义内容更新仅警告，保留结构与卡片编号校验。该更新不会改变模型输入规格

## Link 独立推进的内容

以下事项由 Link 实现，不再列为 Core 必须提供的真实服务器服务能力

- Start、查询刷新、交互消息及服务器报文布局
- 稀疏字段缓存、实例失效、已知值与未提供值的区分
- Type120、160、165 及提示添加、撤销、移动和公开位置记忆
- 给本地 LLM、AstrBot 和 dsh 的玩家可见观察
- 连接生命周期、超时、旧决策取消与协议错误诊断
- 根据实际输入完整度维护 Link 自己的 V4 推理就绪检查

Core 某个受控来源过滤 Type160，只描述该来源提供的数据。Link 对真实服务器收到的 Type160 独立处理，不沿用该过滤，也不能恢复已经被上游删掉的消息。将来若受控 Core 来源需要给 LLM 额外通知，再按该用途选择既有回调或轻量扩展，不要求为此改造真实服务器兼容层

## 诊断入口的定位

Core 的 `integrations/player_view.py` 可以提供输入来源说明和诊断对照，属于可复用参考。其 `encode_v4()` 的现有限制不会直接作为 Link 全部在线功能的前置条件

Link 3.3.9 起开放玩家可见状态兼容在线推理，原生完整性诊断继续单独保留。当前场面与候选使用已接入的在线映射，无法对齐的转移历史屏蔽；真实服务器覆盖和策略质量继续从运行结果检验，不再以完整内部历史作为联网前置条件

模型可推理、轨迹可确定性重放和数据可用于行为克隆继续分别判断。当前工作不要求打开采集或学习资格

## 后续需要共同确认的具体问题

接着在 Link 推进合法动作、动态状态和历史对照。如果发现某个必需模型字段只能由在线不可取得的私有响应构建，Link 应提供具体字段、差异位置和复现样本，再由 Core 决定既有掩码是否足够、是否提供可复用转换，或是否需要新的模型合同

这类问题只针对模型输入含义，不要求 Core 获取对手隐藏信息，也不要求 Core 维护 Link 的服务器布局和完整网络会话

### 已确认的历史缺口与当前选择

V4 转移历史按双方每次真实决策划分，而真实在线服务器通常不会向 Link 提供对手每次选择的边界。本方两次响应之间可以包含多次对手操作，因此 Link 的可见响应区间不能直接等同原生 V4 历史。Link 已有受控反例回归，确认仅改变这种划分也会导致 `event_*` 编码差异

此前选择先保留在线限制。按最新约定，3.3.9 使用独立的 `player_view_compatible_v1` 推理策略，无法对齐的转移历史采用空历史和关闭掩码，本方响应区间仍只供诊断与 LLM 使用。结构合同不变，兼容输入不声称与原生完整历史等价；历史缺失的策略影响尚未量化。Core 无需为此新增服务转换层或复现对手私有响应

## Core 待核对：Type12 效果询问的描述编号读取

Link 3.3.5 对照 Core 提交 `2b754769077470edf4a08f9f09b7ed7f25f2035d` 的当前源码时，发现 `gamestate.py` 中 `MSG_SELECT_EFFECTYN` 动作分支存在读取错位。此项已在 Link 修正，Core 仍保持只读

当前固定载荷为 13 字节：玩家 1 字节、卡密 4 字节、控制者／区域／序号／位置各 1 字节、描述编号 4 字节。Core 长度定义已经是 13，但该动作分支在读完序号后直接读取描述编号，遗漏位置字节。参考客户端 `integrations/windbot/vendor/Game/GameBehavior.cs` 的 `OnSelectEffectYn` 明确读取了该字节

可独立复现的载荷：

```python
payload = bytes([0]) + struct.pack('<IBBBBI', 14558127, 0, 4, 0, 8, 0x01020304)
```

预期 `desc_id=0x01020304`，当前 Core 分支读成 `0x02030408`，并留下最后一个描述字节未读。这会影响效果描述与效果槽绑定，不会改变 Yes／No 应回复 1／0 的规则。这里的位置字节属于有效载荷，不能归为本地定界；Type31 也需区分真实面板标志，见下文修正说明

Core 侧可在序号之后、描述编号之前补读位置字节，并核对受控来源确实遵循这一载荷合同。随后回归效果槽绑定和历史描述引用；无需由 Link 修改 Core 代码或新增真实服务器服务层

`tests/test_v4_prompt_projection.py` 的 Link 侧测试正常校验正确描述与效果槽。只读 Core 对照仅在精确复现上述错位值时标记两项预期失败，分别对应双方座位。Core 修正后会自动进入正常的 108 项编码对照，其他不明差异仍会使测试失败

3.3.6 本轮读取到的 Core 工作区已经通过上述 Type12 双座位对照，本段保留初次发现时的复现说明；Core 侧最终确认仍由其维护方完成

## Core 待核对：排序响应与候选描述的对应关系

本轮只读参考的 Core `rule_bot.py` 排序宏候选将目标顺序中的 `idx` 直接依次写出；参考客户端 `GameBehavior.cs` 的 `OnCardSorting` 则按原始候选索引保存新名次。两种数组互为逆排列，三元素环才能暴露差别

例如原候选 `[A, B, C]`，展示的目标顺序为 `[C, A, B]`。网络应回复每个原候选的新名次 `[1, 2, 0]`。直接回复目标索引 `[2, 0, 1]` 虽能通过排列合法性检查，却对应另一个结果，容易出现无报错但执行顺序不同的现象

Link 在 3.3.6 独立修正这一对应关系，生成器的 `macro_target_codes`／位置按目标顺序保存，`decision_bytes` 按原索引名次保存，三循环回归验证二者可互相还原。Core 侧可检查其排序宏生成段及展示日志，本轮不修改 Core

复杂选择数量、必选占位、精确和及 SumGreater 的边界同时参考 [YGOPro Core playerop.cpp](https://github.com/Fluorohydride/ygopro-core/blob/master/playerop.cpp)。Link 的线上响应使用精确长度，不复制 Core 本地 512 字节填充缓冲；这些参考不自动改变其他真实服务器消息布局

3.3.8 将相同名次向量规则扩展到 Type21。依据 [EDOPro 兼容模式读取](https://github.com/edo9300/edopro/blob/master/gframe/duelclient.cpp) 与 [排序交互响应](https://github.com/edo9300/edopro/blob/master/gframe/event_handler.cpp)，连锁排序的自定义响应同样按原候选保存新名次。兼容模式仍是一字节数量和七字节候选，没有采用 EDOPro 宽字段布局

WindBot 的 `OnChainSorting` 选择 `-1`，含义为默认顺序。Link 将该出口作为附加 `MACRO_SORT` 候选，不套用通用取消操作，避免历史中的取消标志和末端回退证据失真。当前只读 Core 的排序生成器不含这一默认候选，因此原生输入对照只比较自定义排列，默认出口通过 Link 的网络提交及历史回归单独验证

同一实体可能对应多个排序项，七字节提示没有效果描述编号。Link 只增加观察元数据中的原提示索引，不为 V4 张量新增字段或虚构效果身份；更精细的模型识别能力需由模型合同另行决定

## 在线隐藏查询行

此处的查询指 `MSG_UPDATE_DATA`／`MSG_UPDATE_CARD` 携带的卡片状态行，是 YGOPro 网络协议内容，与模型是否采用 V4 无关。“隐藏查询行”是本文的描述用语，“未支持字段位”是 Link 自己的解析检查结果，均不是新增 OCG 指令或服务端错误类型

3.3.10 对照 [YGOPro 服务端查询刷新](https://github.com/Fluorohydride/ygopro/blob/master/gframe/single_duel.cpp) 的 `RefreshHand`、`RefreshMzone` 和 `RefreshSzone`：服务端可以保留卡片查询行的四字节长度头，再将整行其余字节清零。因而长度为 80、字段位图为零的行可以表示一个隐藏卡片占位，不是 Core 本地定界字节，也不是空槽

Link 在在线查询分行层接受长度大于 8 且头部之后全部为零的行，保留占位并清除旧动态字段，即使启用了查询缓存合并也不复用此前身份。四字节行仍表示空槽；3.3.12 起普通在线查询也允许有界尾部，处理方式见下文，原生查询默认解析行为不变

消息回调显式关闭连接时，停止旧连接分发并丢弃其待处理队列，避免状态重置后继续消费旧查询或发起决策。自然远端断开仍保留此前按序处理已收有效消息的行为

## 传统服务器查询保留位

3.3.11 修复在线字段白名单过严的问题。Core 本地请求所需的字段集合不等于真实服务器可能回传的全部位图，两者分别维护

YGOPro 的传统掩码 `0x781FFF`、`0x181FFF`、`0xF81FFF` 带有 `0x100000` 位。对照 [服务端刷新](https://github.com/Fluorohydride/ygopro/blob/master/gframe/single_duel.cpp)、[内核 get_infos](https://github.com/Fluorohydride/ygopro-core/blob/master/card.cpp) 及 [客户端 UpdateInfo](https://github.com/Fluorohydride/ygopro/blob/master/gframe/client_card.cpp)，这一实现会回传该历史位，但不为它写入或读取单独字段。Link 允许该位出现在网络查询头中，继续按已定义字段精确消费整行，不为它增加字段、推定公开身份或调整 V4 张量

3.3.11 当时对其他未支持位和未消费尾部仍采用拒绝策略，3.3.12 改为下述兼容策略。诊断继续给出十六进制字段位图、行长、行号、玩家、区域及消息类型，不打印完整卡片载荷。日志未包含具体位图时，不能把某个保留位缺口当成已确认的实际报文内容

回归使用独立固定的服务端掩码和字段布局，并构造与常见日志同长的手牌及额外刷新，再通过真实 TCP 交给 PTH／ONNX 运行时。它覆盖本次明确缺口，不代表已经录得或完整验收用户本机服务器的实际字节流

## Link 在线兼容策略

3.3.12 起，服务端实现细节差异默认作为警告处理，线上连接不以复现 Core 本地序列化结果为前提

| 收到的差异 | Link 行为 |
| --- | --- |
| 记录长度完整，已声明字段之后还有数据 | 读取已知字段，按原始行长推进，跳过尾部并记警告 |
| 未适配的附加查询位 | 按已知字段读取，保留数值诊断，不因未知位本身断开 |
| 单行边界完整，但字段截断或变量列表无法解码 | 将该卡片记录降级为未知占位并清除旧动态字段，其他记录继续处理 |
| 内层位置与刷新头不一致 | 采用外层刷新头定位并记警告 |
| 槽位数量变化、扩展槽位或连续区空槽 | 接受可解析占位并记警告 |
| 未适配的辅助区域或 Start 之前的查询刷新 | 忽略该辅助刷新并记警告 |
| 重复 Start | 忽略重复通知，保留进行中的场面 |
| 行头截断、长度越过当前报文或无法拆分消息边界 | 仍作为解析异常停止该连接，避免串读和错误响应 |

未声明尾部不是可直接交给模型的属性来源，也不因为出现某个保留位就推定隐藏卡片公开。模型运行时的固定张量结构和当前玩家操作归属仍按实际运行要求处理，信息完整性不足本身不作为在线连接的拒绝条件

独立服务和直接运行入口会将兼容警告保存到 `logs/protocol_warnings.log`，路径相对 `GALATEA_LINK_DATA_DIR`，未设置时相对项目根目录。单文件上限 2 MiB，保留三个备份；同类警告记录前三次及之后每一百次，快照的 `online_coverage` 同时保留完整累计数和最近十六条元数据。日志目录已经被 Git 忽略，不写入卡号、聊天、密钥或原始报文

## 提示消息与拆分诊断

3.3.13 增加网络提示的独立兼容处理。[YGOPro 提示](https://github.com/Fluorohydride/ygopro/blob/master/gframe/single_duel.cpp) 使用四字节数据，[EDOPro 提示读取](https://github.com/edo9300/edopro/blob/master/gframe/duelclient.cpp) 同时支持四字节与八字节数据。旧布局的六字节提示载荷与宽布局的十字节提示载荷不能混用长度；宽提示数据中的 `0x04` 被当作开局指令时，可以出现 `offset=7 Type 4` 截断，但仅凭这一错误不能确认现场首条类型

在线入口先尝试既有布局完整拆分，失败时只尝试有明确结构的宽提示布局，不扫描载荷字节作重同步。宽普通提示不会替换操作菜单；尚未映射到旧状态语义的宽玩家提示只跳过该项元数据，其他已正确拆分的消息继续处理

首条为纯辅助信息，且失败前没有解析出游戏状态或操作菜单的帧，可以降级为 `auxiliary_frame_skipped` 警告。该范围包括普通提示、卡片提示、玩家提示、显示字符串及卡片展示，不扩展到操作菜单、Start、移动、回合或胜负等消息。合并帧内已存在游戏状态消息时，不将整个帧当作纯提示丢弃

边界诊断记录 `first_type`、`previous_type`、`previous_payload_bytes`、`packet_bytes`、`failed_type`、`offset` 和 `remaining_bytes`，用于定位前一条长度是否计算错误。它们沿用协议日志，不包含卡片内容或原始十六进制

## Type31 真实面板标志修正

3.3.14 核对实际十一字节帧的错误轨迹，并对照 [YGOPro 服务端](https://github.com/Fluorohydride/ygopro/blob/master/gframe/single_duel.cpp) 与 [EDOPro 兼容读取](https://github.com/edo9300/edopro/blob/master/gframe/duelclient.cpp)：当前 Type31 的头部是 `player:uint8、skip_panel:uint8、count:uint8`，每张卡片随后占七字节。`skip_panel` 是真实协议字段，不是 Core 本地缓冲区增加的字节。此前将在线 Type31 固定为两字节头的判断有误

Link 使用独立 `core/confirmation_protocol.py` 统一拆分长度、状态更新与公开信息解析，优先识别当前带标志布局并兼容旧版无标志头。对局记录已识别的头部长度，遇到合并消息时按该布局解析；失败后可以尝试另一种明确布局，不扫描任意卡号字节寻找指令。语法上有歧义的合并帧需要已识别布局，不能仅凭任意数据中的一个零／一保证唯一推断

面板标志仅影响客户端展示，不改变 Link 已经收到的公开卡片身份。尚未进场的衍生物确认进入 LLM 的近期展示通知和卡片目录，保留实际接收者可见性，不提前生成场上实体。展示信息不清空正在等待决策的操作菜单

本轮 Core 的 Type31 字段解析和长度计算只读对照均通过，未发现同类 Core 解析错误。详细范围与结论单独列在 [Core 解析核对记录](CORE_PARSER_REVIEW_2026-11-05.md)

## Type16 逐候选强制标志修正

3.3.15 对照 [YGOPro 服务端长度](https://github.com/Fluorohydride/ygopro/blob/master/gframe/single_duel.cpp) 和 [客户端连锁读取](https://github.com/Fluorohydride/ygopro/blob/master/gframe/duelclient.cpp)，按十一字节头、十四字节候选读取当前连锁询问。头部第三字节是特殊候选数，强制标志属于每个候选；模式和强制各一字节，卡号、原始位置及描述各四字节

Link 的 `core/chain_protocol.py` 共用于拆包、动作与规则回退，保留十三字节候选／头部全局强制标志的旧版兼容。单候选完整帧为二十六字节，不能把最后一个描述字节拆成另一条消息。非空列表被识别后，候选宽度记录在本局 `chain_entry_size`；空列表无法区分两种布局，不更新该值。歧义合并帧优先采用本局已识别布局，失败可尝试另一种完整布局，不通过扫描原始字节寻找新指令

强制标志取所有候选的逻辑或，存在强制项就不提供取消；特殊候选数、各候选模式与双方提示时机传入动作元数据及 LLM 观察。V4 取消动作保留 Core 原生未设置的响应特征，实际发包仍为负一。Core 只读字段／长度及双方座位、强制和非强制的全部一百零八项输入对照均通过，未发现同类 Core 缺陷，见 [独立核对记录](CORE_PARSER_REVIEW_2026-11-05.md)

## Type162 玩家场面重建

3.3.16 使用独立 `core/reload_protocol.py` 消费当前传统 YGOPro 的固定七怪兽槽、八魔陷槽，规则号不控制消息宽度。对照本仓库 `ygopro-core-master/field.cpp` 的 `reload_field_info` 和 `ocgapi.cpp` 的 `query_field_info`；当前只读 Core 的读取器也使用同一槽位布局。尚未适配的其他服务器快照格式不能仅按规则号猜测

快照完整解析后原子恢复双方基本分、五类连续区域数量、场上表示与素材数量、当前连锁，未给出卡号的卡片只有未知占位。旧身份、目标装备关系、手牌记忆、未证实的剩余构筑及近期事件清除，本方初始构筑保持不变；玩家级提示没有撤销通知，不能因快照未重复它们就删除。回合和阶段不在此快照内，不从规则号补造

重建前取消未完成推理，移除 Retry 可复用的旧菜单与分支重试状态，不发送额外响应；下一个真实交互再创建新决策。当前连锁标记为 `snapshot`，没有收到的发动确认、结算或无效通知不补造为历史

数量与可界定标志的差异只记兼容警告；实际字段截断继续报告解析错误。Start 之前的完整快照只警告忽略，不据此认领玩家座位。当前只提供玩家视角重建，观众席的 Start、隐私范围与无动作评测仍待独立实现
