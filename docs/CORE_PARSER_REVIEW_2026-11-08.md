# 2026-11-08 Type83 状态异常核对

## 结论

本次用户日志中的退出由 Link 3.4.1 新增的查询失效与公开指示对象跟踪衔接造成，未发现 Core 具有同样的比较逻辑，**不属于本次已确认的 Core 共性解析缺陷**。没有修改 Core，也没有更改 Type83 二进制布局或 V4 模型输入合同

修复列入 Link 3.4.2 更新记录，并随 3.5.0 观众席批次提供

## 故障路径

1. 卡片查询已建立 `query_sequence`，后续卡片移动使该区域中的缓存失效
2. Link `core/gamestate.py::_invalidate_query_facts` 将受影响条目的 `query_sequence` 设为 `None`，表示它不能再作为新的实际查询证据
3. 随后的 Type83 公开指示调用 `core/current_context.py::_capture_chain_target`，通过查询序号判断身份是否在区域失效之后得到刷新
4. 原代码 `entry.get('query_sequence', -1) <= dirty_sequence` 只处理字段缺失，不能处理字段存在但值为 `None`，因此抛出 `TypeError`

旧 GameState 包装把所有更新错误称为「解析错位」，但这份日志实际已经成功拆分消息，故障发生在状态维护中。单纯放宽拆包或忽略未知类型不会修复它，也不应凭此断言服务器发送了错误帧

## Core 对照

只读检查 Core 根目录 `gamestate.py::_capture_chain_target`：Core 根据区域是否在 `_chain_target_dirty_zones` 中决定能否读取身份，没有 Link 用于在线逐槽查询校准的 `query_sequence` 比较，因此不存在这次 `None <= int` 的相同触发路径

Link 需要处理独立在线查询的失效和重新校准，不能把 Core 的区域级方法直接替换过来并假定网络查询时序完全相同。这是实现差异，不是要求 Core 增加 Link 服务转换层

## 修复与验证

- 非整数或空查询序号不参与比较，对应身份保持未知，等待真实刷新；不将空值转换为“刚刷新”的证据
- 新查询到来后仍可恢复可追踪对象身份，不丢弃整条 Type83 公告
- 状态异常附带失败消息类型，保留原始异常链；会话结束说明不再将所有状态错误归因于玩家视角或二进制错位
- 双座位单元场景覆盖移动失效、Type83 公告和新查询恢复；真实 TCP 连续决策覆盖 PTH、新旧 ONNX 的相同状态序列，验证后续仍由 Core 路径完成响应
