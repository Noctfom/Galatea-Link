# 2026-11-08 素材取消闭环核对

## 现场现象与结论

用户在纯 Core 贪心模式中遇到反复特殊召唤、取消、返回主菜单的情况，决策请求编号持续增长，场面没有推进。日志中的稳定路径为：Type11 的特殊召唤索引 4，回复 `01000400`；Type26 的取消候选，回复 `FFFFFFFF`；随后服务器重新提供相同主菜单

这段日志没有出现 `MSG_RETRY` 拒绝提示，反而完整进入素材菜单并接受取消，因此当前证据指向合法响应形成的策略闭环。本次找到并复现的缺陷是 Link 的防循环状态键回归，未发现 Core 同样的全局计数重置问题；没有修改 Core 或服务器消息格式

本地保存设置为贪心、防循环开启、阈值 5 次，不是默认开关未开启。末尾 `KeyboardInterrupt` 来自手动终止，不是这条循环的触发原因

## 原因

3.4.1 补充当前上下文时，将 `prompt_context`、`recent_chain_targets` 和 `resolving_chain_index` 加入 Link `CoreBranchRetry.world_key`

素材菜单里的选择用途与返回主菜单时不同，这是正常提示生命周期。但旧实现每次发现整个 world key 改变，就清空路径、累计次数及软避让。因此进入 Type26 会清空主菜单路径，取消回 Type11 又清空一次，默认阈值永远无法达到。新增上下文本意是区分不同用途，却误把临时菜单变化当作实际场面推进

用户日志没有原始消息正文，不能据此逐字节还原当时的提示参数。回归独立构造相同候选形状、选择用途及查询刷新时序，旧实现可稳定复现同类保护失效；不将测试载荷声称为现场抓包

## Link 3.5.1 修复

- 实际场面仍使用全局、实体、连锁、效果历史及长期公开事实判断，真实进展继续清空旧回退证据
- 选择用途、公开指示和处理链号进入具体提示节点身份，保留完整消息类型、玩家和原始载荷；不会合并相同菜单下不同用途
- 临时进入和退出选择不再清空整条路径，返回同一节点且有取消／撤选证据时累计闭环
- 默认五次阈值不变，先避开末端取消，再尝试其他素材；末端可编码候选耗尽才向上调整入口
- 正常首次取消、无回退证据的连续选择、服务器硬拒绝、失败写出及旧对局回调仍沿用原有边界
- 触发日志增加消息类型和候选编号，事件继续只包含结构信息，不输出卡组或原始消息正文

不强制禁用合法取消，不改变 Core 贪心／温度策略，不通过启用 LLM 或规则接管掩盖循环

## Core 只读对照

Core 根目录 `model_versus.py::ArenaBranchRetry._world_key` 没有把临时选择用途放入全局场面键。测试只在内存编译 `_freeze_arena_state` 与 `ArenaBranchRetry` 的原始定义，不导入 Core 或生成其缓存，再输入相同状态更新和取消路径

Core 原始竞技场在第五次回退正常产生 Type26 末端软避让，旧 Link 对应回归失败。由此确认本次需要修复的是 Link，未发现需要交给 Core 修改的同类问题；这不是对全部 Core 防循环场景的完整审计

## 验证与现场复核

`tests/test_branch_retry_context.py` 覆盖十候选主菜单、二十四字节 Type26 帧、双方座位、查询序号刷新、不同提示上下文节点隔离，以及 Core 原始竞技场对照

TCP 场景使用真实 V4 PTH 和修订 14／15 ONNX。测试权重故意令合法动作同分，使贪心稳定优先进入特殊召唤、随后优先取消，以便验证回退而非随机脱离。双方座位共六组均检查实际网络响应：前五次取消被保留，第六次素材菜单改选素材，再完成下一条询问；十三个响应全部来自 Core，不调用 RuleBot

现场建议重启整个服务确认版本 `3.5.1`，保持纯 Core 贪心和原阈值，重走原先特殊召唤及素材选择流程。若再次形成同局面取消闭环，应出现类似日志

```text
🔁 [Core 闭环回退] 同局面累计 5 次，优先尝试末端其他候选；软避让 Type 26 选项 [0]
```

这表示第五次完整取消返回之后调整，下次再次进入对应素材菜单时生效，不是五条任意决策请求。模型也可能在此前主动改选，此时没有回退日志是正常情况

若仍反复取消且没有该日志，保留从首次进入异常菜单开始的操作日志、运行版本和脱敏事件；若已触发但继续在更深素材选择间往返，也应保留后续菜单，以区分不同分支回退与其他真实状态变化
