## 资产与导入

V4 必需文件为：

- `card_vocab.json`：从保留 token 后开始连续编号的精确词表
- `semantic_lookup_v1.npz`：已经编译的数值语义表
- `semantic_lookup_v1.json`：语义身份、效果槽和提示来源等轻量目录

`cards.cdb`、`meta_staples.json` 和包内源语义资产可一并导入。编译语义是推理必需输入，Link 不会因为缺少文件而自动重建或退回 V3 资产。V4 必需校验也不受 `strict_asset_hashes=false` 绕过

在 WebUI 的模型仓库导入 Core 生成的 GKG4，再选择模型即可保存路径。模型位于 `models/`，资产位于 `model_assets/v4/<model_id>/`；V3 继续使用 `model_assets/v3/<model_id>/`。卡密 token 继续只追加，语义内容更新按下方合同校验

PTH 使用安全权重加载并严格匹配网络参数。ONNX 要求同轮 `.artifacts.json`、主图和声明的全部外置权重；图内模型身份与制品身份必须一致。创建 ONNX Runtime 会话前检查外置引用、文件名和字节范围

V4 模型的资产页会说明需导入匹配的 GKG4，并禁用 V3 卡库及语义重建入口，避免旧维护器写坏当前模型资产。142 兜底池仍可独立调整

### 语义内容更新

新版 GKG4 可以携带 `semantic_compatibility_v1.json`。Link 合并同模型池已有的历史证据并检查冲突，原始部署包和权重文件保持原样

| 制品 | 内容变化后的处理 |
| --- | --- |
| PTH | 核验原始卡密前缀、标签编号前缀、编码器、分块策略和向量维度后，允许使用新语义表 |
| ONNX | 图内语义保持导出时内容，外部语义演进和词表追加只警告，导出后新增卡片按未知卡编码 |

PTH 缺少兼容证据或编号、坐标系变化仍会拒绝加载。ONNX 从 3.3.3 起允许外部语义内容演进，不要求 Link 重新导出，也不修改图内身份。图与同轮制品清单仍必须一致，输入结构、词表容量、既有卡片编号前缀和外置权重完整性继续严格校验，词表重排或结构变更不能按普通更新放行

ONNX 运行时公开 `asset_compatibility`，`warning=true`、`status=frozen_onnx_outdated` 表示知识滞后，附新增卡片数、语义内容是否变化和说明。加载日志、模型详情与 GKG 导入结果显示同一警告；导入结果的 `warnings` 不影响导入成功。旧图不具备新卡语义，旧卡被修正的语义也未写回图中，不能保证影响仅限新卡。需要新知识时可从 Core 获取更新后的 ONNX，Link 不负责重导出

同池只有 ONNX 时，可以更新外部资产而保留旧图；无法合并的旧语义兼容证据由新包的自洽目录替代。池中仍有 PTH 时，资产替换继续满足 PTH 的编号和向量坐标系兼容要求。资产自身的逻辑哈希不匹配、文件缺损仍会拒绝，不把坏文件当作更新

PTH 兼容更新后的运行状态保留制品原身份，另提供 `runtime_asset_identity` 和 `semantic_update`，控制台也会提示预测可能随新知识变化。ONNX 使用 `runtime_asset_identity` 和独立的 `asset_compatibility`，不会报告已经采用新图内语义

## 离线验证

只读制品目录即可验证，不需要将 Core 加入 `PYTHONPATH`。将下面路径换成自己的模型和资产位置

```powershell
python scripts/test_model_protocols.py path/to/galatea_iter_210.pth --assets path/to/core_assets --full
python scripts/test_model_protocols.py path/to/galatea_iter_210.onnx --assets path/to/core_assets --full
```

ONNX 使用 `requirements-onnx.txt`，包括 ONNX 图检查库和 ONNX Runtime，不安装 Torch。PTH 使用 `requirements-pytorch.txt`

脚本构建的是人为指定的离线测试快照，仅用于核对加载、字段编码和前向运算。它不能证明服务器能够提供全部在线输入。真正的在线接入仍经过单独的玩家观测检查

3.3.0 在相同语义资产下对第 210 轮 V4 PTH／ONNX 做了 CPU 离线对照：最小测试快照的合法动作 logits 最大差约 `1.34e-7`，value 差约 `2.98e-8`。3.3.1 已用该 PTH 与 Core 当前更新后的资产验证兼容加载和前向推理；更新后的 PTH 不应再要求与冻结旧语义的 ONNX 数值一致。这些结果不代表策略质量或真实在线覆盖率

## 在线解析改动

`core/online_state.py` 与模型编码器独立维护服务器公开状态，目前提供以下基础能力：

- Start 精确读取 18 字节载荷，固定玩家物理座位及双方 LP、主卡组和额外数量
- Type6 整区刷新、Type7 单卡刷新先验证整包再提交，整区刷新会清除空槽
- Type6 按兼容服务器的独立 `STOC_GAME_MSG` 载荷解析；其他封包布局需要单独的报文配置和样本
- 保留实际发送的字段集合和查询序号，动态等级、攻击力等已知零不再被数据库默认值覆盖
- LLM 观察只输出查询已知的动态值，未提供的值保持缺失；身份静态资料仍由卡库提供
- 查询不会生成新动作，也不会让正在等待的后台决策重新排队
- 传递查询中的阶级、连接值、状态位、指示物、所有者及原始位置关系；装备来源与被装备实体分别处理
- 移动、交换、洗牌或表示变化会清理受影响实例的旧查询，同时清除其他实体指向旧位置的关系，保留无关卡片的有效查询
- 已失效查询在 LLM 观察中标记 `query_invalidated`，旧攻击力等动态字段保持缺失，等待服务器刷新
- 3.3.4 将 Type93／95／96／97 的装备和目标事件同步到原始位置及既有查询缓存，已解除关系不会被增量刷新复活
- Type71／72／73／75／76 的公开连锁进度独立提供给 LLM；不写入模型原生历史，不把结束通知当作效果成功
- 对手隐藏信息和主卡组查询身份不会进入公开投影
- 未确认缓存合同时默认保守处理，不从字节猜测增量合并；`replace`、`merge` 是内部适配合同，尚未开放任意用户切换
- Type120、160、165 由 Link 独立处理，不沿用 Core 受控消息源的过滤器，也不因为收到提示就额外排队决策
- 维护卡片数值提示、描述引用、玩家提示、公开顶卡、卡组反转、抽卡与洗牌失效；空槽和明确换卡移除旧实例提示
- 提示与记牌按实际消息接收者绑定，隐藏宿主不会借提示泄漏身份；玩家查看限制由明确通知添加或撤销
- 分开记录回合玩家、先手玩家和当前决策者，LLM 观察新增 `public_context`

观察增加 `information_quality.online_coverage`，报告固定座位、Start 是否收到、查询合同是否确认和当前限制。它会明确保留 `online_v4_inference_ready=false`，不是供调用者修改的完整性声明

生产消息拆分遇到未知类型或截断会记录解析失败，取消旧决策、清空旧动作、结束本局连接并记录 `protocol_error`，避免继续消费错位字节。当前只保留原有在线 Type16／Type31 布局，没有照搬 Core 原生布局或重新猜测幽灵字节

## 诊断映射与导出

`model_protocols/v4/online_adapter.py` 将当前 Link 快照映射为独立 V4 结构。它保留合法动作次序和响应字节，按 V4 的定义补齐 Idle 操作语义、关系与己方初始构筑。额外区查询产生的纯库存实体不会重复进入实体表，隐藏身份仍按当前消息接收者裁剪

映射中的未知值只用于检查结构。报告对全局、卡片、动作、卡组、连锁、效果历史、响应区间和公开上下文逐组列出来源完整性；`mapped=true` 表示能够映射，不表示输入已经完整。所有投影均带诊断标记，正常 V4 编码入口会拒绝，不能通过修改报告中的就绪字段开启推理

WebUI 的“模型仓库 → V4 在线接入检查”可查看摘要并导出 JSON。任意 V3 或仅 LLM 对局均可生成报告，不需要加载 V4 模型。接口为 `GET /api/v1/models/diagnostics/v4`，使用现有服务令牌；返回 `data` 中的 `galatea.v4_observation_diagnostics.v1` 报告

报告仅含座位、数量、字段缺口、位置坐标和机器可读阻塞原因，不含卡密、卡名、卡组、LLM 输入正文、网络响应字节或密钥。它只在服务内存保留，导出由用户主动执行；停止游戏会话后可导出上一局，重启服务后不保留。报告不自动附加到 LLM 请求

常见字段：

| 字段 | 含义 |
| --- | --- |
| `available` | 已收到 Start，当前或最近一局有诊断数据 |
| `scope` | `current_duel` 本局，`last_duel` 最近结束的一局，`none` 无数据 |
| `groups.cards.missing_attributes` | 前 120 张可见卡片的缺失字段和坐标，不含卡密 |
| `groups.actions.legacy_chain_semantics_unverified` | 当前链选择沿用旧在线布局，V4 语义仍待服务器样本核验 |
| `groups.transitions` | 已完成响应区间数量、未映射候选、截断及发送／重建缺口 |
| `blocking_reasons` | 尚未完整的输入组、容量溢出或映射失败原因 |
| `online_inference_ready` | 当前固定为 `false`，不因受控样本对照一致而开启 |

## 本方响应历史的边界

Link 在网络发送前创建草稿，成功写出并收到下一次本方提示、Retry 或胜负消息后才发布不可变记录。查询、读取快照和空连锁不会切出新决策；写出失败、取消和重置不会补记为成功。每局最多保留最近 16 个区间，每区间最多 256 条、256 KiB 可见消息，超限区间只报告缺口，不当作完整事件编码

这里的“成功写出”并不代表服务器接受了动作，Retry 会作为明确的拒绝边界记录。候选只按实际发出的响应唯一匹配，不能确认时标为未映射，不猜测 RuleBot 使用了哪个动作

V4 原生历史按双方每次真实决策划分。真实在线服务器通常不会告诉 Link 对手的每次选择边界，本方两次响应之间可能包含多次对手操作。本方区间即使覆盖了公开事件，也不能代替原生历史。回归包含一个反例：局面、动作等其余输入相同，但区间划分不同会改变 `event_*` 编码

当前选择保留 V4 在线推理限制，继续完善 Link／LLM。暂不更改 Core 的历史合同，不构造对手私有响应，也不为绕过限制新增 Core 服务转换层。将来是否提供在线可见历史合同，需另行讨论模型输入语义

3.3.6 再覆盖十种复杂场景的双方座位，共二十组 108 项基础输入对照：多选、普通／双倍解放、指示物、带必选的精确和、仅必选素材、SumGreater、双值 SumGreater、Type25 卡片排序及 Type26 选撤。最终宏响应另按原生约束与独立组合规则检验，不把基础动作对照误作全部最终宏模型输入等价证明

3.3.7 在相同独立预期响应和展示元数据上执行 Core 原始宏构建器，十三类场景的双方座位共二十六组最终宏候选各 108 项输入一致，包含前述复杂宏选择及区域、种族、属性；另对大候选池使用相同顺序和随机种子，验证缩减结果一致。这不等于两侧全部候选枚举策略相同，也不证明超过上限的所有组合都已覆盖

大池缩减固定保留取消响应，剩余容量再按权重无放回采样。末端优先闭环回退自 3.3.3 接入，本批补充宏池重排后的软禁用迁移与空字节完整响应身份回归；开关和阈值继续使用原有统一配置，不新增一套参数

3.3.8 新增 Type21 的基础和自定义最终宏候选双座位对照，共四组各 108 项一致。自定义宏仍在同一独立预期候选上执行 Core 原始构建器，Link 附加的服务器默认顺序候选单独验证其响应、提交历史与操作语义，不将其声称为 Core 已有候选

Type21 只接收当前 YGOPro 兼容的玩家一字节、数量一字节、每项七字节布局；没有启用 EDOPro 的宽字段原生协议。依据 [EDOPro 兼容读取](https://github.com/edo9300/edopro/blob/master/gframe/duelclient.cpp) 和 [排序响应](https://github.com/edo9300/edopro/blob/master/gframe/event_handler.cpp)，自定义结果使用每个原候选的新名次，`-1` 表示默认顺序。Link 用 `MACRO_SORT` 记录该出口，不标为取消效果，不作为末端回退证据

LLM 通过 `sort_operation` 区分默认与自定义顺序，`selection_items[].prompt_index` 保留排序项的原始身份。重复实体不合并，提示本身没有效果描述时明确标记缺失；菜单顺序不等同于已经观察到的实际连锁及结算

诊断的 `groups.actions.candidate_stage` 区分 `base_candidates` 基础评分候选、`explicit_responses` 显式完整响应和 `direct_candidates` 可直接选择的候选。`selection_response_checks` 表示对应类型在最终提交时还会校验实际响应；这些字段都不授予在线推理权限

实现约束如下：

- Type20 的最小值是解放值，最大值约束张数；末字节不是表示形式
- Type22 按原候选顺序回复逐项 uint16 数量，零分配不从网络向量删除
- Type23 必选素材保留占位，可选素材仍使用可选列表索引，求和不允许取消；SumGreater 不误用包内 max 限制数量
- Type25 展示目标顺序，网络按原候选的名次向量回复，空响应保持为字节而不是整数零
- Type26 完成／取消出口置顶，候选总数超过八位索引容量时明确拒绝，不把越界选择伪装成取消
- 规则回退和候选生成复用同一合同，最终写出前复核，求和复核在线程内执行且受时间和搜索预算约束

新生成器默认最多保留 5000 个已验证候选、100000 个搜索状态，随后仍由既有策略缩减至模型容量。同名墓地、场上及已知状态不同的副本不合并，达到上限时不能据此宣称枚举了全部选择。Core 仍只读，网络响应不使用本地固定长度填充

对照结果只包含字段名、形状、类型、差异数量和少量差异索引，不包含实际编码值，也不运行模型前向。受控夹具没有覆盖全部真实服务器消息、复杂选择、双方历史或策略质量，不能据此宣布在线适配完成
